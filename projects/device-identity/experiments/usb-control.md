# USB control-pipe identity inventory

Request plan revision 2 uses bounded descriptor prefixes followed by declared
lengths. Revision 1, frozen at `c21e458`, obtained a native device descriptor but
its 255-byte LANGID request returned `kIOReturnNotResponding`; the bridge's five
requests succeeded. That whole capture remains failed. This diagnostic changes
request sizing without assuming the cause or reconfiguring the board.

Decision question: what serial descriptors does the attached USB host obtain
through explicit control requests, and can the CP2102N part/configuration be
read without opening, seizing or reconfiguring either device?

The [USB/eFuse inventory](read-only-inventory.md) and
[runtime table experiment](runtime-table.md) observed macOS enumeration
properties. Those properties can be cached. Reuse their target IDs and ownership
domains, while making this observation path an explicit default-control-pipe
request rather than an IORegistry string query. No existing RF result or
performance number is compared.

## Observer and fixed inputs

The observer is the attached Mac using `IOUSBDeviceInterface942.DeviceRequestTO`.
The selected macOS SDK 27.0 header documents that this function can issue read
requests without opening the device. Bindings are generated by bindgen 0.72.1
with libclang 21.1.8; provenance retains SDK/header and generated-binding hashes.
Rust 1.96.0, edition/style 2024 and the project lock pin the host implementation.
Offline record parsing and synthetic controls also run on Linux, where native
observation is unsupported.

Registry properties select exactly one native `303a:1001` and one bridge
`10c4:ea60` service. They do not supply the reported descriptor strings. Zero or
multiple matches, setup failure, transfer error or cleanup failure remain failed
observations. No fallback opens or seizes a device. COM `Release` frees plugin
and device references: `IODestroyPlugInInterface` is excluded because it can
stop an associated service. The collector calls no reset, configuration setter,
kernel-driver detach, interface claim or serial control-line operation.

Requests occur synchronously on the main thread with initialized bounded output
buffers and explicit transfer timeouts. Returned length must fit the requested
buffer. No callback or borrowed pointer survives a synchronous call. OS I/O can
overrun a requested timeout; no hard real-time bound is claimed.

These observations are at the OS control-request boundary. They do not provide
a USB bus trace or independently qualify the host kernel's caching behavior.
The application source and recorded setup packets establish that convenience
cached-string getters were not the observation path.

## Read-only request plan

For each selected device, the same planner drives live I/O and saved replay:

1. Standard device-recipient IN `GET_DESCRIPTOR(DEVICE)`, requesting 18 bytes.
   Validate descriptor type/length, endpoint-zero size, configuration count and
   the fresh VID/PID against the selected domain. Obtain `iSerialNumber` from
   these bytes.
2. If `iSerialNumber` is nonzero, request a four-byte STRING-zero prefix. Require
   type three and an even declared length from four through 254; if it exceeds
   four, fetch exactly that length and require the repeated prefix to agree.
   Validate the complete nonzero unique LANGID table. Read a two-byte serial
   STRING prefix using the fresh index and first advertised LANGID, then fetch
   its declared even length (two through 254) when longer than the prefix.
   Require repeated-prefix equality, complete framing and valid UTF-16LE.
   No serial index means no language or
   serial request and a distinct `absent` observation, not an error or anonymity
   claim. Empty and nonempty serial contents remain distinct. The four-byte
   LANGID prefix has [libusb precedent](https://github.com/libusb/libusb/blob/v1.0.30/libusb/descriptor.c#L1234);
   this does not establish that revision 1's larger request violated USB rules.
3. For the bridge only, issue vendor/device IN request `0xc0/0xff`, value
   `0x370b`, index zero, one byte. Require part code `0x20`, `0x21` or `0x22`
   before issuing the CP2102N configuration read. Other parts remain unsupported.
4. Read exactly 678 bytes with the same vendor IN request, value `0x000e`, index
   zero. Require configuration layout version one at byte two. Report only
   whether byte four equals its documented `0xff` default. This is not a lock
   interpretation. No configuration-write or older `GetLockValue` API is used.

The vendor blob has deliberately limited interpretation. Actual length and
layout version are checked; configSize field endianness, checksum byte order,
lock state, uniqueness and programming permissions are unqualified. The complete
blob remains private for future source-qualified interpretation. The older
lock API explicitly excludes CP2102N; a readable configuration does not prove
that writing is permitted.

## Qualification and collection

Before hardware access, qualify the actual planner, capture/save/replay CLI and
native ABI with synthetic passing and contrary controls. Include wrong IN/OUT
direction, VID/PID mismatch, overrun/short lengths, duplicate/invalid LANGIDs,
wrong selected language, invalid UTF-16, unsupported part/layout, setup/cleanup
failures, reordered/missing/extra records, unknown versions/fields, redacted
Debug and malicious private sentinels. Deliberately failed transfers stop that
domain's request sequence and stay in the raw record. A separate reviewer
checks generated layouts, COM ownership, allowed calls and saved replay.
Prefix/body controls additionally reject malformed/short prefixes, odd/oversized
declared lengths, changed repeated headers, truncated full bodies and changed
LANGID prefix contents. Raw and capture versions distinguish the revised plan;
older records are not silently reinterpreted.

Freeze the method, source, lock, native provenance and collector identity before
two complete read-only captures of the same attached devices. Use a new ignored
private directory for each attempt. No firmware change or deliberate reset is
part of this baseline. Abort this cohort on its first failed capture. Preserve
all failed attempts; investigate unexpected failures before repeating collection
or changing the method.

Capture creates private storage and a raw output file before native observation.
The complete raw record, native provenance, sanitized summary and completion
receipt form an exact four-file inventory. A successful replay must validate
the receipt, record semantics and saved summary equality. Tampered, incomplete
or failed captures cannot be admitted by dropping a failed domain. Standalone
record summaries do not authenticate capture origin.

Compare the two validated records by decoded serial contents and complete bridge
blob equality. Publish only fixed `unchanged`/`changed`/`unavailable` states,
counts and documented layout metadata. No raw strings, configuration bytes,
device paths, registry identities or hashes of private USB contents reach the
public report. Stable serial contents do not establish population uniqueness.

No driver MAC change, on-air receiver, reconnect/cold boot, descriptor write or
rotation result follows from this baseline. A later table/driver comparison must
freeze its own schedule, retain startup/recovery evidence and use an independent
observer for transmitted identities.

## Conditional ROM-state diagnostic

If revision 2's original-state native LANGID request again returns
`kIOReturnNotResponding` while the complete bridge subset validates, stop that
cohort and perform one separately labeled ROM-state capture. This is a different
device state, not a retry admitted into the original-state baseline. Other
failures do not trigger this branch.

Use the previously qualified bridge UART and pinned esptool 4.12.0, with an
explicit empty `[esptool]` configuration that excludes local reset overrides.
Set `ESPTOOL_OPEN_PORT_ATTEMPTS=1` explicitly as well as the CLI connection bound.
Retain hashes of the configuration, executable and selected entry/reset source
files before collection. Entry uses `--chip esp32c6 --baud 115200 --no-stub
--connect-attempts 1 --before default_reset --after no_reset read_mac`, with the
private bridge port supplied explicitly. Require zero exit and the expected
C6/ROM/no-stub completion before the single USB capture. Keep all output private.
This opens the bridge UART and resets the C6, destroying its current RAM state.
It does not upload a stub or request flash/eFuse/bridge-configuration content
writes. Esptool's ROM setup can attach the flash controller, reset the flash
chip and issue XMC-specific flash power-state commands.

After any entry attempt, always attempt a separate cleanup command using the
same port/options but `--before no_reset --after hard_reset read_mac`, including
when entry or capture failed. Record command, times and exit status. Admit host
reset-sequence completion only with zero exit, the expected hard-reset notice
and no unexpected warning or error, including the suppressed `Chip was NOT reset`
warning. Allow only the exact standard pre-connection `no_reset` warning that
connection may fail outside bootloader/stub mode. Reject other warnings/errors
case-insensitively, especially unsupported RTS/DTR or a chip that was not reset.
The notice precedes the line toggles and is not a physical acknowledgment.
Esptool reaches its `--after` action only after a successful operation; merely
attempting cleanup does not establish host reset-sequence completion. A failed
cleanup leaves recovery unresolved and requires investigation. Warning-free
host completion supports the intended release to the original flash application;
physical boot, subsequent health, radio traffic and persistence effects remain
unmeasured. No independently verified
postboot storage-equality claim follows from the absence of tool-directed
content writes.

## Sources and publication

- The selected installed SDK's `IOUSBLib.h` and generated bindings, identified
  by the collector's native provenance. The current SDK's no-open request
  contract is the selected input; older web header descriptions can differ.
- [Linux v6.12 CP210x driver](https://github.com/torvalds/linux/blob/v6.12/drivers/usb/serial/cp210x.c)
  supplies the part codes and CP2102N request tuple/length.
- [Silicon Labs AN978](https://www.silabs.com/documents/public/application-notes/an978-cp210x-usb-to-uart-api-specification.pdf)
  defines the configuration fields and older lock API exclusions. The checksum
  algorithm's presence does not establish the unresolved blob byte order here.
- [libusb v1.0.30 Darwin implementation](https://github.com/libusb/libusb/blob/v1.0.30/libusb/os/darwin_usb.c)
  documents why its plugin path uses COM release rather than destroying the
  associated service. Its enumeration/open side effects are not reused.

Keep raw responses and diagnostics under ignored `private/device-identity/`.
The public result owns its scoped claims, source freeze and a complete seal
covering every retained regular file except the seal. Read-only replay and seal
verification do not open devices, repair failures or manufacture observations.
